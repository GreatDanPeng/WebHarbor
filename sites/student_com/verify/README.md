# student_com — reviewer grading contract

Authored by the reviewer on `orch/review/student_com` (reviewer track). The
contributor's `tasks.jsonl` rows keep their original 5 keys
(`web_name, id, ques, web, upstream_url`) byte-for-byte as the JSON prefix; the
reviewer appended exactly `verifier_path` and `judge_rubric` per row. There is
**no `answer` key** — ground truth lives only in the verifiers.

## Layout

- `verify_lib.py` — shared deterministic utilities: fail-closed package
  identity (task_id, `terminated`+`agent_done`, non-empty answer, same
  loopback origin+port, decodable PNG screenshots), navigation gates,
  token/phrase/number answer checks, and the SQLite after-state contract.
- `verify_0.py … verify_20.py` — one deterministic verifier per task
  (generated by `make_verifiers.py`; regenerate with `python3 make_verifiers.py`).
- `append_rubrics.py` — the tasks.jsonl merge (5-key prefix preserved).
- `tests/` — `test_verifiers.py` + `_support.py` + `fixtures_data.py`
  (frozen honest trajectories from the reviewer's live Playwright walks).

Run the contract tests (needs the review container for the seed, or point
`STUDENT_COM_TEST_SEED_DB` at a copy of `instance_seed/student_com.db`):

```
python3 -m pytest sites/student_com/verify/tests -q
```

## Seed contract

The student_com seed build is **not byte-reproducible at the SQLite file
level** (four clean `PYTHONHASHSEED=0 seed_data.py` rebuilds produced four
different file md5s — the physical page layout varies run to run), but the
logical content is stable. The contract therefore freezes the logical digests
(computed with the exact functions in `verify_lib.py`):

- `SCHEMA_SHA256` over `sqlite_master`
- `SEED_ROWS_SHA256` over every row (table-canonical, ORDER BY all columns)
- `SEED_COUNTS` per table

Both digests were verified to reproduce across independent rebuilds. Do not
"fix" the contract by freezing a file md5 — it will not reproduce.

## After-state model

Opening a property page records a `property_views` row (`record_view()`
commits before render — including on the pages that currently crash with
HTTP 500). The per-task contract therefore allows exactly:

- read-only tasks: every table row-identical to the seed;
- browsing tasks: only `property_views` grows, by exactly the property pages
  the trajectory visited;
- stateful tasks: the exact bookmark / enquiry / registered-user delta plus
  the expected `property_views` rows, and nothing else.

The enquiry reference is deterministic from the seed (enquiries id 1-4 are
seeded, so a fresh-state inquiry is id 5 → `INQ-000005`). Bookmark deltas are
checked with set semantics on `(user_id, property_slug)` because SQLite
reuses the max rowid (remove-then-add rewrites the same row id).
